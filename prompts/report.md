작성 규칙
1. SUMMARY 는 "상황 → 결론 → 근거 → 리스크 → 요청" 순서의 5줄이고, 상황·결론·요청 줄과 장 번호 '(→n장)'은 시스템이 붙인다. 너는 구절만 쓴다.
{% if mode == 'hold' %}
   - common_cause (90자 이내): 후보들이 기준에 못 미친 **공통 원인** 한 구절 (근거 id). 점수·비율은 되풀이하지 않는다.
{% else %}
   - ev_tech · ev_market · ev_team (각 70자 이내): 결론을 뒷받침하는 **확인된 사실** 한 구절씩 — 기술·차별성 / 시장 규모·성장 / 팀(창업 전 경력·기술 역량). 근거 id 를 붙이고, ev_market 은 문서([D..]) 수치로 쓴다.
   - risk_line (90자 이내): 투자 전에 가장 먼저 확인할 리스크 1~2개를 한 구절로 (근거 id).
   - lead_idea · lead_market · lead_team (각 60자 이내): 1·2·3장 첫 줄에 굵게 들어갈 **결론 한 문장**. 장의 내용을 예고하지 말고 판단을 쓴다 (나쁜 예: "이 장에서는 시장을 살펴본다" / 좋은 예: "세부 시장은 연 15% 성장 중이나 규모 추정치가 기관마다 다르다").
{% endif %}
   - "본 보고서는", "이 보고서는 ~를 판단하는", "~을 살펴보면", "개요", "이 장에서" 같은 **보고서·장 소개 문장은 절대 쓰지 않는다.**
   - 평가표 용어 "UNKNOWN" 은 쓰지 말고 "공개 근거 없음" 또는 "미확인"이라고 쓴다.
   - 제품 성숙도(PoC·실증·시제품·상용)는 평가표 P1(상용 운영) 판정과 같게 쓴다. P1 이 YES 가 아니면 "상용 운영 중"이라고 쓰지 않는다 (예정이면 "상용화 예정").
2. 모든 사실·수치 문장 끝에 근거 id 를 대괄호로 붙인다. 예: "...[D1a2b3]". 근거 목록에 있는 id 만 쓰고, 그 문장의 사실이 실제로 적힌 근거를 고른다.
{% if mode == 'hold' %}
3. candidates: 평가한 후보마다 하나씩, 이름은 위 후보별 요약의 이름 그대로 쓴다.
   - business (50자 이내): 사업 한 줄 (한국어).
   - why_not (1~2문장): 그 후보의 **결정적 반대 근거(NO)**와 **확인되지 않은 핵심 항목**을 사실로 쓴다. 반대 근거 문장에는 근거 id 를 붙인다. 점수·비율·보류 유형은 쓰지 않는다 (시스템이 붙인다).
   - 그 후보의 평가표에서 YES 가 아닌 항목(특허·매출·고객 수·차별성 등)을 확인됐다고 쓰지 않는다. 검색 실패 표시가 있는 후보는 근거 부족을 회사 탓으로 단정하지 않는다.
   common_detail (2~3문장): 공통 원인과 시장 맥락(투자 조정 국면 포함)을 근거 id 와 함께 쓴다.
{% endif %}
4. 사업 아이디어 ({{ target }}): problem(해결하는 문제), product(제품·핵심 컨셉), revenue_model(수익 방식 — 근거 없으면 "확인 불가").
   회사 홈페이지·보도자료에만 있는 내용은 "회사 측 설명에 따르면"처럼 **회사 주장**임을 밝힌다.
   industry_baseline: 업계(문서 [D..])가 말하는 기술 과제·상용화 수준과 비교해 대상이 어느 단계인지 한 문장.
5. market (2~4문장): 세부 시장 규모·성장·수요(지불 의향)를 **공공·연구기관 문서([D..])** 수치로 쓰고, 투자 사이클(조정 국면) 근거가 있으면 한 문장 더한다.
   - 수치마다 기준 연도·기간과 추정 기관을 밝힌다. 미래 연도 수치는 "전망"이라고 쓴다.
   - 이미 지난 기간의 전망(작성일 연도보다 앞선 연도의 전망)을 쓸 때는 반드시 같은 문장에 "(20XX년 발표 전망)"처럼 **발표** 시점을 밝힌다. 더 최신 수치가 근거에 있으면 그것을 쓴다.
   - 정의가 다른 시장(예: 애그테크 전체, 스마트농업, 농업 로봇)을 한 문장에 나란히 두지 말고, 각각의 범위를 밝힌다.
6. team (2~3문장): 창업 시점(t0) 이전의 경력과 이후의 실행(마일스톤)을 나눠, 대표·기술 책임자의 **이름과 경력**(근거 id)으로 쓴다. 팔로워·조회수 같은 누적 인기 지표는 쓰지 않는다. 확인되지 않은 것은 "확인 불가".
7. competition (1~2문장): 경쟁 구도와 진입장벽 요약 (경쟁사 표는 시스템이 붙인다).
   competitor_notes: 경쟁사 표의 회사마다 하나씩 (회사명 그대로: {{ competitor_names }}). vs_target 은 대상과 비교한 사실 한 문장.
   평가표 C2(경쟁사 대비 차별점)가 YES 가 아니면 "앞선다·우위·차별화된다" 같은 우열 표현 없이 제품·접근·대상 작물의 **차이만** 쓴다.
8. risks: 시장·기술·규제·경쟁 유형별로 1개 이상. 각 리스크에 evidence_ids(1개 이상)를 달고, due_diligence 에는 실사에서 회사에 확인할 질문을 쓴다. 규제 리스크는 스마트농업법·기본계획 문서 근거를 우선 쓴다. 표 안에서도 7번의 우열 표현 규칙을 지킨다.
9. data_limits: 이 회사·시장 데이터의 한계 1개 (검색 실패·방법론 한계는 시스템이 붙인다).
10. 문체: 간결한 보고서체. "우수하다·탁월하다·뛰어나다·혁신적인" 같은 평가 형용사를 쓰지 말고 사실로 쓴다.
